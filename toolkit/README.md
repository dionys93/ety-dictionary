# Etym-Toolkit: Inglisce Dictionary CLI & Translation Engine

A specialized Bash, Node.js, and Python toolkit for managing, auditing, and exporting the **Inglisce Etymological Dictionary**, alongside a deep-learning translation pipeline for full-text books.

The library is built around a single canonical parser (`etym-parse`, implemented in `etym-parse.awk`) that every other function consumes, ensuring consistent data across all lookup, analysis, and build operations. Presentation is handled entirely by Astro.js; this toolkit's job stops at producing clean, structured JSON and translated text data.

---

## 📁 Repository Structure

* **`data-text/inglisce/dictionary/`** — Core dictionary data organized by alphabetical subdirectories (e.g., `a/animate.txt`).
* **`data-text/histories/`** — Per-definition history files split out by `etym-create-histories`.
* **`data-text/books/`** — Raw English source texts (e.g., Sophocles, Shakespeare) waiting to be translated.
* **`data-text/inglisce/books/`** — The final transcribed Inglisce text files.
* **`toolkit/.cache/ast-books/`** — Intermediate build artifacts (JSON Abstract Syntax Trees) generated by the Python NLP engine.
* **`toolkit/.cache/morpholex/`** — The MorphoLex-en workbook and the flat lookup file `etym-morph --setup` builds from it.
* **`toolkit/venv/`** — The Python environment (step 1 below). The toolbelt finds it on its own, activated or not.
* **`toolkit/config/`** — Central configuration for paths (`env.sh`) and lookup tables (`languages.tsv`, `language-aliases.tsv`, `parts-of-speech.tsv`, `affixes.tsv`).
* **`toolkit/etym-lib.sh`** — The core Bash toolbelt for word lookup, validation, and JSON/CSV compilation.
* **`toolkit/etym-parse.awk`** — The canonical stanza parser (strictly POSIX awk — runs identically under gawk, mawk, and macOS awk). The single source of truth for the JSONL schema; edited and golden-tested directly.
* **`toolkit/scripts/`** — The Polyglot Build Pipeline:
  * `translate-books.sh` — The master orchestrator for the translation pipeline (fails fast per phase; never transcribes a stale AST cache).
  * `spacy_parser.py` — Python deep-learning NLP parser (spaCy).
  * `transcriber.js` & `utils.js` — Node.js functional transcription and morphological mapping.
  * `build-dictionary.js` — Compiler for the translation brain (Phase 2 below).
  * `cmu_pron.py` — CMUdict lookup and ARPAbet→IPA conversion behind `etym-pron`; `sounds.py` builds and searches the pronunciation index behind `etym-sound`, reusing it.
  * `morpholex.py` — MorphoLex-en setup and lookups behind `etym-morph`.
* **`toolkit/dist/`** — Automated build output: the master JSONL dataset, `translationBrain.json` (lemma keys sorted for clean git diffs), the `missing_words.txt` / `fallback_words.txt` trackers written by the transcriber, and `pronunciations.tsv`, the index `etym-sound` searches (rebuilt automatically when the dictionary changes).
  * `dist/api/` — `navigation.json` and `letters/*.json`, per-letter entry data for the frontend. No script in this toolkit writes them, so they come from outside it; treat them as read-only here.
* **`toolkit/tests/`** — Vitest test suite covering the Bash pipeline and translation layer (see **Testing** below).
* **`toolkit/debug/`**, **`toolkit/lint.txt`** — Scratch output from past runs. Not inputs to anything; safe to delete.

## 🚀 Installation & Setup

Because this project utilizes a polyglot architecture (Bash, Node, and Python), you must set up environments for both the frontend API build and the heavy NLP translation engine.

**Steps 1 and 2 are per machine. Steps 3 and 4 are per shell.** Installing is
what you do once; activating is what every new terminal, tab or SSH session
needs again. On Codespaces the installed side lives under `/workspaces`, which
survives stopping, restarting and rebuilding the container — only deleting the
codespace takes it with you. Nothing in steps 1 and 2 needs repeating at login.

### 1. The Python Environment — *per machine*
The translation engine relies on a Python deep-learning Dependency Parser, and
the pronunciation and morphology commands use two small Python packages. All of
it goes in one virtual environment, **`toolkit/venv`**.
```bash
# Navigate to the toolkit
cd /path/to/project/toolkit

# Create the virtual environment
python3 -m venv venv
source venv/bin/activate  # (On Windows: venv\Scripts\activate)

# The translation engine: spaCy and the heavy Transformer model
pip install spacy
python -m spacy download en_core_web_trf

# The dictionary's Python helpers
pip install cmudict      # etym-pron, etym-sound
pip install openpyxl     # etym-morph --setup (reads the MorphoLex workbook once)
```
`en_core_web_trf` is a transformer and the download is large, so this is the
step worth not repeating. The `source` line above is here only because `pip`
needs the environment active to install into it — as an activation it is step 3's
job, not this one's. To be sure a package lands in this environment whatever
`pip` is first on your PATH, install through its interpreter:
`toolkit/venv/bin/python -m pip install cmudict`.

One more per-machine step needs the toolbelt, so it comes after step 3: run
**`etym-morph --setup`** once to download MorphoLex-en and build its lookup file.

### 2. The Node.js Environment — *per machine*
Required for dictionary compilation and applying Inglisce suffixes.
```bash
npm install
```

### 3. The Shell Session — *per shell*
Nothing is installed here; these lines put an already-built environment in front
of the current terminal, and every new terminal starts without them:
```bash
source toolkit/venv/bin/activate   # the Python env from step 1
source toolkit/etym-lib.sh         # the CLI toolbelt
```
Sourcing the toolbelt never prompts or installs anything. If a dependency is missing (`jq` is required for most functions; any POSIX awk suffices for the parser), a warning lists what's absent — run **`etym-install-deps`** to install interactively, or install manually. Set `ETYM_QUIET=1` to suppress the sourcing banner (useful in scripts and CI).

Phase 3 of the translation pipeline is the only thing that needs the Python
environment *activated*. `etym-pron`, `etym-morph` and `etym-sound` also run
Python, but they find the environment themselves, so a shell that only runs
`etym-*` commands can skip the first line. They use, in order: `$ETYM_PYTHON` if
set; an active venv (`$VIRTUAL_ENV`); `toolkit/venv`, `toolkit/.venv`, `venv` or
`.venv` at the project root; and finally `python3`. When a package is missing,
the error names the interpreter it checked and gives the exact command to
install into it, and lists every place it looked for a venv if it found none.

### 4. Configuration — *per shell*
`toolkit/config/env.sh` derives most paths from its own location, but **`DICT_DIR` defaults to an absolute Codespaces path** (`/workspaces/ety-dictionary/data-text/inglisce/dictionary`). Working anywhere else, export it before sourcing the library, or every lookup will silently find nothing:
```bash
export DICT_DIR="$PWD/data-text/inglisce/dictionary"
source toolkit/etym-lib.sh
```
**The part-of-speech register.** `toolkit/config/parts-of-speech.tsv` decides which `(pos)` tags are legal; `etym-lint` warns on any tag in the dictionary that is missing from it. It is hand-edited, so the format is deliberately loose — one tag per line, `<tag> - <description>`, with `#` comments and blank lines ignored and alignment free:

```
m n     - masculine noun
v - verb
intr v  - intransitive verb
```

A tag may contain spaces (`m n`, `def v`) but never a hyphen, which is what makes the dash an unambiguous boundary; the previous whitespace-separated form could not distinguish `def v defective verb` from `defin definite article` without already knowing the answer. Legacy tab-separated rows still parse. Every consumer reads the file through `_pos_rows` / `get_pos_desc` in `env.sh` — nothing greps it directly, because three places once held their own copy of the parsing rule and one of them disagreed.

Note that passing lint does not guarantee a record survives the build: `scripts/build-dictionary.js` keeps its own `posMap`, and `suffix`, `prefix`, `interj`, `obs`, `def v` and `indef` are registered in the TSV but absent from it, so `buildBrain` drops those records regardless.

**The language register.** `toolkit/config/languages.tsv` decides which `[TAG]` language tags are official, one per line as `TAG  Name`. `toolkit/config/language-aliases.tsv` lists retired tags, either with a replacement or with the reason the tag should not be used at all. For example:

```
MD    MDU
FRK   (Frankish is reconstructed: stop the chain at the oldest attested form)
```

A retired tag should not also be registered. `etym-lint` checks every tagged line against both files, and `etym-langs` shows which tags the data actually uses — the evidence for deciding what goes in them.

`ETYM_AWK` overrides which awk runs the parser; `ETYM_LIB_DIR` is recomputed from `BASH_SOURCE` at source time, so its default in `env.sh` is never used.

The Python helpers read a few more, all optional:

| Variable | Sets | Default |
|---|---|---|
| `ETYM_PYTHON` | the interpreter for `etym-pron`, `etym-morph` and `etym-sound` | found as described in step 3 |
| `ETYM_CMUDICT` | a local `cmudict.dict` file to read instead of the package, e.g. offline | the `cmudict` package |
| `ETYM_MORPHOLEX` | the MorphoLex lookup file | `toolkit/.cache/morpholex/morpholex.tsv` |
| `ETYM_SOUND_INDEX` | the pronunciation index | `toolkit/dist/pronunciations.tsv` |

## 📖 The Translation Pipeline

Two sides feed one transcriber, and neither knows the other exists until they
meet. The **dictionary side** reduces stanzas to a lookup table: English lemma
in, Inglisce form and conjugations out. The **book side** turns English prose
into tagged tokens: what each word is, and what it is doing in its sentence.
Phase 4 is the only place both are in the room.

```
DICTIONARY SIDE — what a word becomes
  data-text/inglisce/dictionary/*/*.txt
        │  ① etym-build-dataset  (etym-parse.awk)
        ▼
  dist/master_dataset.jsonl          one record per stanza; etymology + sources
        │  ② build-dictionary.js  (buildBrain)
        ▼
  dist/translationBrain.json         lemma → { Verb: "bêne", Verb_conjugations: … }

BOOK SIDE — what this sentence is doing
  data-text/books/*.txt
        │  ③ spacy_parser.py  (en_core_web_trf)
        ▼
  toolkit/.cache/ast-books/**.json   one record per token: lemma, pos, tag, transitivity
        │
        └────────────┬───────────  ④ transcriber.js  ←── translationBrain.json
                     ▼
  data-text/inglisce/books/*.txt
```

**Phase 1 — Dataset (awk).** `etym-build-dataset` crawls the dictionary and
writes `dist/master_dataset.jsonl`, one record per stanza, carrying everything
the `.txt` files hold.

**Phase 2 — Brain (Node).** `node toolkit/scripts/build-dictionary.js` reduces
that dataset to `dist/translationBrain.json`. This is a **lookup table, not an
archive**: etymology and sources are dropped, and any stanza whose `(pos)` tag
is absent from the script's own `posMap` is dropped with them. The brain is the
only part of the dictionary the transcriber can see.

**Phase 3 — AST (Python/spaCy).** `spacy_parser.py` reads English and nothing
else — it has never heard of Inglisce. Its job is to say which word is present
and what it is doing: `lemma` so the brain can be searched by dictionary form,
`tag` so the transcriber knows past from gerund, `transitivity` so a verb with
separate transitive and intransitive stanzas gets the right one, `is_ent` so
proper nouns are left alone.

**Phase 4 — Transcription (Node).** `transcriber.js` walks the cached AST,
looks each lemma up in the brain, applies the morphology `utils.js` describes,
and writes `data-text/inglisce/books/`.

`translate-books.sh` runs **only phases 3 and 4**. Phases 1 and 2 are the
dictionary's own build and are run separately, by hand or by whatever changed
the dictionary. If either of its phases fails the pipeline aborts immediately,
names the phase that died, and propagates the exit code, so Phase 4 can never
run against a partial AST cache.

```bash
./toolkit/scripts/translate-books.sh
```

### What to re-run when

| You changed | Re-run |
|---|---|
| a dictionary `.txt` file | 1 → 2 → 4 |
| `etym-parse.awk` | 1 → 2 → 4 |
| `build-dictionary.js` (`posMap`, the reducer) | 2 → 4 |
| `spacy_parser.py` (the AST schema) | 3 → 4 |
| a book under `data-text/books/` | 3 → 4 |
| `transcriber.js` or `utils.js` | 4 |

Phase 4 alone is `node toolkit/scripts/transcriber.js <ast_dir> <out_dir>`, which
is worth knowing because Phase 3 is the slow one: `en_core_web_trf` is a
transformer, and **`.cache/` is not incremental** — `spacy_parser.py` rglobs
every `.txt` under the books directory and rewrites every AST on every run.
There is nothing to invalidate, and nothing to delete. To try a change against
one book, point Phase 3 at a directory holding a single file.

### Trackers

Two files land in `dist/` after every transcription run, and both are printed to
the terminal as well:

* **`missing_words.txt`** — every English word no brain entry answered, sorted
  and deduplicated. This is the queue of words to add to the dictionary next.
* **`fallback_words.txt`** — every word served by a different part-of-speech
  category than spaCy detected (an adjective token answered by a noun entry, say).
  The first place to look when a translation reads strangely.

Both are deleted rather than left stale when a run produces none.

## 🛠️ CLI Toolkit Commands

### Core Engine & Parsing
* **`etym-parse <file.txt>`**
  The canonical stanza parser. This is the single source of truth for reading `.txt` entries. It emits one JSONL record per stanza to standard output, handling complex verb conjugations, irregular plurals, and nested etymologies. `conjugations` is always a named JSON object (never a raw array). Stanzas it cannot classify safely produce a stderr warning rather than a silent guess.

### Browsing & Lookup
* **`etym-cat <word>`**
  Prints the raw stanza content of a word's file, including automatically generated stanza numbers.
* **`etym-find <query>`**
  Performs a recursive **literal** search across the entire dictionary. Accepts raw text or language tags (e.g., `[OE]`) — tags match exactly, and punctuation in queries is never interpreted as a pattern. Searches every line of every file, etymology and sources included; to search headwords alone, use `etym-select`.
* **`etym-info <word> [--brief|--chain|--json] [--no-sources]`**
  Outputs one numbered block per stanza, so a word with several parts of speech shows which descent chain belongs to which definition. Default mode prints a summary table (Inglisce form, Part of Speech, Language Origin, conjugated forms) followed by a detail block per stanza; `--brief` prints the table alone, `--chain` prints the descent chains alone, and `--json` emits the selected records as a JSON array for piping into jq. `ORIGIN` is the **oldest** attested language in the chain.

  This replaces the former `etym-chain <word>`, which no longer exists as a separate function — use `etym-info <word> --chain`.
* **`etym-cognates <root_word>`**
  Searches the entire dictionary's ancestry to find all modern Inglisce words that share a common ancestor — searching `tabula` returns `table`, `tablet`, `tabulate` and `tabele`. Matches against etymology forms and Inglisce forms, not against the headword, and the query is treated as a case-insensitive regex.

### Data Analysis
* **`etym-summarize [path] [--json] [-o <file>]`**
  Prints high-level dictionary statistics including Parts of Speech frequency, Language Origin distribution, and a Cross-Tabulation matrix of the top POS × Lang combinations.
* **`etym-affix [path] [--prefix|--suffix] [-n <len>] [-p <pos>] [-l <lang>]`**
  Performs a morphological frequency analysis to calculate the most common prefixes or suffixes across the dictionary, with optional filtering by Part of Speech or Language Origin.
* **`etym-select [pattern] [--starts|--ends|--exact] [--fold] [--length <n|n-m|n+>] [-p <pos>] [-d <path>] [--me|--inglisce] [--pos] [--bare|--count|--json]`**
  Selects entries by their **headwords only** — the `[ME]` line and the reformed line — and prints both sides of the reform for each. This is the narrow counterpart to `etym-find`: a search for `cion` there returns etymology forms, Middle English spellings and source URLs alongside the reformed forms you wanted, because it greps whole files.

  ```bash
  etym-select cion --inglisce          # reformed forms containing "cion"
  etym-select cion --inglisce --ends   # ...ending in it
  etym-select tion --me                # English headwords containing "tion"
  etym-select c̃ --inglisce             # every form carrying c-with-tilde
  etym-select ough --me --length 6     # two criteria at once
  etym-select --length 4-6             # length alone
  etym-select cion --inglisce --bare   # pipeable list of matches
  etym-select -p irv                   # every irregular-verb stanza
  etym-select -p 'irv,tr irv,intr irv' # all three irregular tags at once
  etym-select ough --me -p 'intr v'    # pattern and tag together
  ```

  `--me` / `--inglisce` picks the side that is **searched, measured and sorted**; both columns print either way. At least one of a pattern, `--length` or `-p` is required.

  **`-p` selects on the POS tag; `--pos` only prints the column.** Selecting turns the column on by itself. Matching is per tag, not substring: a stanza tagged `(aux, v)` is found by `-p v`, and `-p v` does not find every adverb. Repeat the flag or pass a comma-separated list to accept several tags. Every tag is checked against `parts-of-speech.tsv`, and an unregistered one is an error rather than an empty table. The path is `-d/--dir` rather than a positional, unlike `etym-affix` and `etym-summarize`, because a pattern and a path are both arbitrary strings and `etym-select cion s` could not otherwise be told from a two-word query.

  **Checking a rule against itself.** The pairing of criteria is what makes this useful for auditing drift: 541 English headwords contain `tion` but only 438 reformed forms end in `cion`, so the difference is a list of words the rule has not reached — or has deliberately been spared.

  **Matching is literal, not regex**, for the reason `etym-find` uses `grep -F`: punctuation in a query can never become a pattern. ASCII case is folded, so the two entries beginning with Cyrillic `Ћ` are reachable by `Ћ` but not by a lowercase form of it.

  **Both query and form are canonically decomposed before comparison.** The dictionary writes the same letter two ways — `â` appears as U+00E2 six times and as `a`+U+0302 a thousand times — so without that step a search for `â` returns six hits of a thousand and reads as a wrong answer rather than an encoding mismatch. The table in `jq_defs` covers the base+mark combinations the orthography currently uses and must be extended alongside it.

  **By default the pattern then matches the form as written, marks included**, so `c̃` finds c-with-tilde rather than every c. The cost is that a query spanning a marked letter can miss: `ac` will not match `âc`, because a combining circumflex sits between the two letters. `--fold` strips marks from query and form alike, which makes `ac` match `âc` — and makes `c̃` match every c, so use it knowingly.

  **Length means letters, not bytes or codepoints.** `tône` is five codepoints and four letters; since roughly 40% of reformed forms are accented, a raw count would be wrong more often than right. Marks, hyphens and stray punctuation are stripped before counting and again for the sort key, so `âge` files at 3 and sorts at "age" rather than after z. Table padding uses display width, so accented rows line up.

  **Rows are deduplicated by headword pair.** The dictionary's ~8,800 stanzas are only ~7,800 distinct English–Inglisce pairs, because some 1,500 headwords carry more than one stanza — without dedupe `like` appears five times. Pass `--pos` for one row per stanza with its part of speech. Genuinely distinct reformed forms still get their own rows (`work → uirc` and `work → uirche` both appear).

  **Caveat inherited from the parser.** `resolve_me_word` keeps only the first comma- or space-delimited token of the `[ME]` line, so multi-word headwords collapse: ten entries match `New` as a prefix (`Noueórc`, `Nouhampsior`, `nouhampsioraït`), and `all` picks up `alraidy`, `altogaiþre`, `alþó`. The reformed side truncates the same way (`beehive → bí`, `toothbrush → touþ`). This is pre-existing behaviour rather than something the selector introduces, but a headword query is where it becomes visible — and worth fixing before anything writes to disk against a selection.

  Selection is the durable part of this function. POS is now one of its criteria, beside `--length`; language origin belongs here too when it lands. Anything that *acts* on a selection belongs downstream of the projection.

### Pronunciation & Morphology
These three read the **whole `[ME]` line**, not the parser's `me_word`, so they escape the first-token caveat above: `can, could, can't, couldn't` gives four words and `New York` one form. They read files through a shared helper that uses `etym-parse.awk`'s own tests for what counts as a reformed line, an `[ME]` line and a POS tag. Only `[ME]` is read, never `[MI]` or older, since both sources describe Modern English. Stanzas are chosen as in `etym-info`: a word matches any comma-separated `[ME]` form or the reformed headword, so `etym-pron could` finds the `can` stanza.

* **`etym-pron <word> [--ipa|--both]`**
  Prints the General American pronunciation of every word on the `[ME]` line of each matching stanza, from CMUdict. The default is ARPAbet with stress digits (`K L OW1 Z`); `--ipa` gives IPA-like notation (`/ˈkloʊz/`), and `--both` shows them side by side. Every CMUdict variant is listed, since the dictionary cannot tell *close* /s/ from /z/ by part of speech, and words it lacks are marked rather than guessed.

  **"IPA-like" is deliberate.** The symbols are a direct mapping, split by stress where CMUdict uses one symbol for two sounds: `AH0` is /ə/ and `AH1` is /ʌ/, `ER0` is /ɚ/ and `ER1` is /ɝ/. R is written ɹ, and the affricates tʃ and dʒ without tie bars. Stress marks are the approximation. CMUdict marks stress on the vowel and says nothing about syllable boundaries, so each ˈ/ˌ is placed by the maximal-onset rule (/ˈɛkstɹə/, /kənˈstɹʌkt/), which can split a word differently from a pronouncing dictionary.

* **`etym-sound [options]`**
  Finds `[ME]` words by how they sound. Sounds may be written in IPA or ARPAbet, and the word `schwa` stands for either unstressed schwa, plain /ə/ or r-coloured /ɚ/.

  ```bash
  etym-sound --schwa-final -p verb    # last syllable is a schwa: widen, bottle, butter
  etym-sound --schwa-end -p verb      # last sound is a schwa: samba, butter
  etym-sound --has aɪ -p noun         # "long i" anywhere: time, pilot, idea
  etym-sound --stressed aɪ -p noun    # ...only where it carries the stress
  etym-sound --ends ən                # same as --ends "AH0 N" or --ends "schwa n"
  etym-sound --starts sk --syll 1     # one-syllable words starting /sk/
  etym-sound --has aɪ --json          # records for jq; --bare and --count too
  etym-sound --missing                # forms CMUdict does not know
  etym-sound --rebuild                # rebuild the index now
  ```

  Each result shows the word, its IPA, your POS, your reformed line and `file:stanza`; `--arpa` adds an ARPAbet column. `-p` takes POS tags as `etym-select` does, plus the groups `noun`, `verb`, `adj` and `adv`, which gather every tag of that kind (`verb` is `v`, `tr v`, `intr v`, `irv` and the rest).

  **Stress in a pattern.** An IPA ˈ or ˌ before a vowel, or an ARPAbet digit (`AY1`), requires that stress; without one, any stress matches. Because ə and ʌ are the same CMUdict vowel told apart by stress, ə only matches the unstressed one and ʌ only a stressed one; likewise ɚ and ɝ. CMUdict writes many reduced vowels as `IH0` (*rabbit*, *wanted*), not `AH0`, so those do not count as schwa.

  **The index**, `toolkit/dist/pronunciations.tsv`, holds one row per pronunciation of every `[ME]` form, with its file, stanza, POS and reformed line. It is plain TSV, fine to grep or open. It is rebuilt automatically whenever a dictionary file or the lookup code is newer than it, so a search never runs on stale data. Forms CMUdict does not know are kept as rows with no pronunciation, so the gaps are countable rather than invisible.

* **`etym-morph <word> [--raw]`** · **`etym-morph --suffix <suffix> [--raw]`** · **`etym-morph --setup [<file.xlsx>]`**
  Morphological segmentation from **MorphoLex-en** (68,624 English words, each with the English Lexicon Project's part of speech). `etym-morph <word>` segments every word on the matching `[ME]` lines: *cleanliness* is `clean + -ly + -ness`, a noun. `--suffix en` lists every `[ME]` word in the dictionary whose segmentation contains that suffix, grouped by part of speech, with your POS tag and `file:stanza` beside each. `--raw` shows MorphoLex's own notation (`{(wood)}>en>`) and ELP codes (`JJ`) instead.

  **MorphoLex segments by spelling**, so every *-en* is the same `>en>` whatever its history. The part of speech is what separates *wooden* (adjective) from *widen* (verb), and the grouping is a first sort, not an etymology. It is a derivational database, so participles such as *broken* may not be segmented at all.

  `--setup` downloads the workbook from GitHub (or reads a local copy) and needs `openpyxl`; lookups need only Python itself. If the workbook's column headers ever change, setup stops and prints the ones it found.

### Build Pipeline
* **`etym-build-dataset [output_file]`**
  Crawls the dictionary directory and writes the master dataset JSONL (default `toolkit/dist/master_dataset.jsonl`). This is the primary input source for Node.js build steps. Runs the parser as a single process over the whole tree.
* **`etym-flatten [path] [--jsonl|--csv] [-o <file>]`**
  A flexible flattening command that delegates to `etym-build-dataset` for JSONL, or compiles the dictionary into `dist/master_dataset.csv` for spreadsheet analysis. The CSV carries only `me_word`, `inglisce_word`, `pos` and flattened `conjugations` — etymology and sources are JSONL-only.

### File Management & Auditing
* **`etym-langs [path] [--json]`**
  A census of the language tags in use: each tag with its count, whether it is registered, retired (and to what), or neither, its registered name, and example lines for every unofficial one. Then the lines the parser cannot read a language from at all: names in brackets (`tomatl [Nahuatl]`) and chain lines with no tag (`τριάς`). The examples matter: the same tag is sometimes used for different languages, and the same language under different tags, so deciding the official set is a judgement the census only makes quick.
* **`etym-lint [path] [--strict]`**
  Scans the dictionary for formatting errors and returns exit code 1 if any `[FATAL]` or `[ERROR]` is found. Checks:
  * `[FATAL]` empty files
  * `[ERROR]` missing or malformed language tag `[]`, and a language tag sharing a line with a POS tag
  * `[ERROR]` a stanza whose conjugation line has no `(pos)` tag — silently dropped by `etym-parse`
  * `[ERROR]` a stanza with no reformed line and no etymology either — malformed rather than unfinished
  * `[ERROR]` a `(pos)` tag that is not at the end of its reformed line — `etym-parse` records an empty `pos`
  * `[ERROR]` source URLs separated from their stanza by a blank line — `etym-parse` reads paragraphs, so those sources are dropped
  * `[WARN]` trailing whitespace, stanzas with no resolvable language tag, and POS tags absent from `parts-of-speech.tsv` (these records are otherwise silently skipped by `buildBrain`)
  * `[WARN]` a stanza carrying etymology but no reformed line — a word not yet reformed. It warns rather than errors, because it is ordinary work in progress, but it warns at all because `etym-parse` drops the stanza and it reaches no dataset.
  * `[WARN]` language tags, checked line by line:
    * a tag missing from `languages.tsv`
    * a retired tag from `language-aliases.tsv`, with its replacement or the reason it is retired
    * a language written as a name in brackets (`[Nahuatl]`)
    * a chain line with no tag at all

    For the last two, `etym-parse` records an empty `lang`. A reformed conjugation line (`to eite -s éit eiten -ing`) is not a chain line and is never flagged.

  Also generates a verb conjugation coverage report highlighting non-standard stanzas. **`--strict` turns the language-tag warnings into errors**, so the run exits 1 while any remain. They are warnings by default because the register is still being settled.

  **The language check reads every line.** The older "no resolvable language tag" check looks only at the last `[ME]`/`[MI]` line of a stanza, so an untagged or name-tagged line further up a chain passes it; the built dataset held 71 such lines when this was added. Both checks remain; the new one says which line and why.

  **POS tag validation uses `etym-parse`'s own regexes**, so lint and parser cannot disagree about what a valid tag looks like. The check this replaced kept a second dialect of them — `\([a-z ]{1,5}(, [a-z ]{1,5})*\)` — which capped every tag at five characters and so rejected `(interj)`, `(suffix)`, `(prefix)` and `(intr v)`, all of which the parser accepts and all of which are registered. Being file-level rather than per-stanza, it also passed a file whenever any one stanza carried a valid tag, so it only ever surfaced on single-stanza files. Shape is settled by the parser's regex; membership is settled by `parts-of-speech.tsv`. Those are the only two authorities and neither restates the other — which is what keeps a bug like that from recurring.

* **`etym-trim [path]`**
  Strips trailing whitespace from all `.txt` files in a directory. Resolves all trailing whitespace lint warnings in one pass.
* **`etym-create-histories [-d] [-v] [--dirs <a,b,c>]`**
  Splits each multi-stanza `.txt` file into individual per-definition history files under `data-text/histories/`, named `<word>_<pos>.txt`. Non-alphanumeric characters in the POS tag become underscores, so `(adj, m n)` yields `..._adj__m_n.txt`. `-d` dry-runs without writing; `--dirs` limits the pass to named letter directories.

### Graphing & Visualization
* **`etym-graph [path] [-o <file>]`**
  Builds a `{nodes, edges}` JSON graph of all etymological relationships across the dictionary, default `etym_graph.json` in the working directory. Requires jq 1.6+ and checks the version explicitly before running.
* **`etym-visualize [graph_file]`**
  Converts a graph file (default `etym_graph.json`) into a Mermaid Markdown file, `etym_graph.md`, for visual preview in modern editors.

## 🧪 Testing

Two entry points, one source of truth:

```bash
npm test                        # full Vitest suite: bash + node + nlp projects
bash toolkit/tests/test-etym-parse.sh   # parser suite with ZERO npm dependencies (CI/quick shell loops)
```

* **Golden files** — every fixture in `tests/fixtures/parser/` (real dictionary entries covering all conjugation classes, hostile escaping cases, and multi-stanza files) is byte-compared against its frozen output in `tests/snapshots/parser/`. To refreeze after an intentional parser or fixture change:
  ```bash
  find tests/fixtures/parser -name '*.txt' | sort | while read f; do
    rel="${f#tests/fixtures/parser/}"
    awk -f etym-parse.awk "$f" > "tests/snapshots/parser/$(echo "${rel%.txt}" | tr '/' '_').jsonl"
  done
  ```
* **Schema contract** — `tests/node/brain-contract.assertions.mjs` pipes the frozen goldens through the real `buildBrain()` and asserts on the compiled brain, catching any drift between the awk parser and its Node consumers. It runs both under Vitest and standalone (`node tests/node/brain-contract.assertions.mjs`).
* **Property & fuzz** — `resolveForm`'s silent-ending rules are exercised across hundreds of seeded generated roots, and random hostile strings are round-tripped through the parser's JSON escaping. Seeds are fixed, so failures always reproduce.
* **Drop accounting** — the parser test asserts that *only* explicitly registered stanzas are ever skipped, so silent data loss in fixtures is impossible.
