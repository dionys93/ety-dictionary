# Etym-Toolkit: Inglisce Dictionary CLI & Translation Engine

A specialized Bash, Node.js, and Python toolkit for managing, auditing, and exporting the **Inglisce Etymological Dictionary**, alongside a deep-learning translation pipeline for full-text books.

The library is built around a single canonical parser (`etym-parse`, implemented in `etym-parse.awk`) that every other function consumes, ensuring consistent data across all lookup, analysis, and build operations. Presentation is handled entirely by Astro.js; this toolkit's job stops at producing clean, structured JSON and translated text data.

---

## 📁 Repository Structure

* **`data-text/inglisce/dictionary/`** — Core dictionary data organized by alphabetical subdirectories (e.g., `a/animate.txt`).
* **`data-text/histories/`** — Per-definition history files split out by `etym-create-histories`.
* **`data-text/books/`** — Raw English source texts (e.g., Sophocles, Shakespeare) waiting to be translated.
* **`data-text/inglisce/books/`** — The final transcribed Inglisce text files.
* **`toolkit/.cache/ast-books/`** — Intermediate build artifacts (JSON Abstract Syntax Trees) generated by the Python NLP engine.
* **`toolkit/config/`** — Central configuration for paths (`env.sh`) and lookup tables (`languages.tsv`, `parts-of-speech.tsv`, `affixes.tsv`).
* **`toolkit/etym-lib.sh`** — The core Bash toolbelt for word lookup, validation, and JSON/CSV compilation.
* **`toolkit/etym-parse.awk`** — The canonical stanza parser (strictly POSIX awk — runs identically under gawk, mawk, and macOS awk). The single source of truth for the JSONL schema; edited and golden-tested directly.
* **`toolkit/scripts/`** — The Polyglot Build Pipeline:
  * `translate-books.sh` — The master orchestrator for the translation pipeline (fails fast per phase; never transcribes a stale AST cache).
  * `spacy_parser.py` — Python deep-learning NLP parser (spaCy).
  * `transcriber.js` & `utils.js` — Node.js functional transcription and morphological mapping.
  * `build-dictionary.js` — Compiles `dist/master_dataset.jsonl` into `dist/translationBrain.json`.
* **`toolkit/dist/`** — Automated build output: the master JSONL dataset, `translationBrain.json` (lemma keys sorted for clean git diffs), and the `missing_words.txt` / `fallback_words.txt` trackers written by the transcriber.
  * `dist/api/` — `navigation.json` and `letters/*.json`, per-letter entry data for the frontend. No script in this toolkit writes them, so they come from outside it; treat them as read-only here.
* **`toolkit/tests/`** — Vitest test suite covering the Bash pipeline and translation layer (see **Testing** below).
* **`toolkit/debug/`**, **`toolkit/lint.txt`** — Scratch output from past runs. Not inputs to anything; safe to delete.

## 🚀 Installation & Setup

Because this project utilizes a polyglot architecture (Bash, Node, and Python), you must set up environments for both the frontend API build and the heavy NLP translation engine.

### 1. The Python NLP Environment (spaCy)
The translation engine relies on a Python deep-learning Dependency Parser.
```bash
# Navigate to project root
cd /path/to/project

# Create and activate a virtual environment
python3 -m venv venv
source venv/bin/activate  # (On Windows: venv\Scripts\activate)

# Install requirements and the heavy Transformer model
pip install spacy
python -m spacy download en_core_web_trf
```

### 2. The Node.js Environment
Required for dictionary compilation and applying Inglisce suffixes.
```bash
npm install
```

### 3. The Bash Toolbelt
Source the library from within the `toolkit/` directory to activate all CLI tools in your session:
```bash
source toolkit/etym-lib.sh
```
Sourcing never prompts or installs anything. If a dependency is missing (`jq` is required for most functions; any POSIX awk suffices for the parser), a warning lists what's absent — run **`etym-install-deps`** to install interactively, or install manually. Set `ETYM_QUIET=1` to suppress the sourcing banner (useful in scripts and CI).

### 4. Configuration
`toolkit/config/env.sh` derives most paths from its own location, but **`DICT_DIR` defaults to an absolute Codespaces path** (`/workspaces/ety-dictionary/data-text/inglisce/dictionary`). Working anywhere else, export it before sourcing the library, or every lookup will silently find nothing:
```bash
export DICT_DIR="$PWD/data-text/inglisce/dictionary"
source toolkit/etym-lib.sh
```
**The part-of-speech register.** `toolkit/config/parts-of-speech.tsv` decides which `(pos)` tags are legal; `etym-lint` warns on any tag in the dictionary that is missing from it. It is hand-edited, so the format is deliberately loose — one tag per line, `<tag> - <description>`, with `#` comments and blank lines ignored and alignment free:

```
m n     - masculine noun
v - verb
intr v  - intransitive verb
```

A tag may contain spaces (`m n`, `def v`) but never a hyphen, which is what makes the dash an unambiguous boundary; the previous whitespace-separated form could not distinguish `def v defective verb` from `defin definite article` without already knowing the answer. Legacy tab-separated rows still parse. Every consumer reads the file through `_pos_rows` / `get_pos_desc` in `env.sh` — nothing greps it directly, because three places once held their own copy of the parsing rule and one of them disagreed.

Note that passing lint does not guarantee a record survives the build: `scripts/build-dictionary.js` keeps its own `posMap`, and `suffix`, `prefix`, `interj`, `obs`, `def v` and `indef` are registered in the TSV but absent from it, so `buildBrain` drops those records regardless.

`ETYM_AWK` overrides which awk runs the parser; `ETYM_LIB_DIR` is recomputed from `BASH_SOURCE` at source time, so its default in `env.sh` is never used.

## 📖 The Translation Pipeline

To translate an entire folder of English books into Inglisce, we use a highly optimized, decoupled 2-step pipeline.

**To run the pipeline:**
```bash
./toolkit/scripts/translate-books.sh
```

### How it works:
1. **Phase 1: Deep Learning (Python):** `spacy_parser.py` reads the English text and uses the `en_core_web_trf` neural network to generate a highly accurate Abstract Syntax Tree (AST). It perfectly identifies Verb phrases, Plural Nouns, and Named Entities, saving them to `toolkit/.cache/ast-books/`.
2. **Phase 2: Transcription (Node.js):** `transcriber.js` consumes the cached AST JSON. It acts as a pure, functional mapper—looking up root words in `translationBrain.json` and applying the correct morphological suffixes (via `utils.js`) without freezing the main thread. It outputs the final `.txt` files to `data-text/inglisce/books/`.
3. **Missing Words Tracker:** untranslated words are aggregated into a globally sorted list in your terminal output **and** written to `toolkit/dist/missing_words.txt`, so downstream tooling knows exactly what words to add to your dictionary next.
4. **Cross-POS Fallback Tracker:** when a word is served by a different part-of-speech category than spaCy detected (e.g. an adjective token answered by a noun entry), the pipeline records it to `toolkit/dist/fallback_words.txt` — the first place to look when a translation reads strangely.

If either phase fails, the pipeline aborts immediately, names the phase that died, and propagates the exit code — Phase 2 can never run against a partial AST cache.

## 🛠️ CLI Toolkit Commands

### Core Engine & Parsing
* **`etym-parse <file.txt>`**
  The canonical stanza parser. This is the single source of truth for reading `.txt` entries. It emits one JSONL record per stanza to standard output, handling complex verb conjugations, irregular plurals, and nested etymologies. `conjugations` is always a named JSON object (never a raw array). Stanzas it cannot classify safely produce a stderr warning rather than a silent guess.

### Browsing & Lookup
* **`etym-cat <word>`**
  Prints the raw stanza content of a word's file, including automatically generated stanza numbers.
* **`etym-find <query>`**
  Performs a recursive **literal** search across the entire dictionary. Accepts raw text or language tags (e.g., `[OE]`) — tags match exactly, and punctuation in queries is never interpreted as a pattern. Searches every line of every file, etymology and sources included; to search headwords alone, use `etym-select`.
* **`etym-info <word> [--brief|--chain|--json] [--no-sources]`**
  Outputs one numbered block per stanza, so a word with several parts of speech shows which descent chain belongs to which definition. Default mode prints a summary table (Inglisce form, Part of Speech, Language Origin, conjugated forms) followed by a detail block per stanza; `--brief` prints the table alone, `--chain` prints the descent chains alone, and `--json` emits the selected records as a JSON array for piping into jq. `ORIGIN` is the **oldest** attested language in the chain.

  This replaces the former `etym-chain <word>`, which no longer exists as a separate function — use `etym-info <word> --chain`.
* **`etym-cognates <root_word>`**
  Searches the entire dictionary's ancestry to find all modern Inglisce words that share a common ancestor — searching `tabula` returns `table`, `tablet`, `tabulate` and `tabele`. Matches against etymology forms and Inglisce forms, not against the headword, and the query is treated as a case-insensitive regex.

### Data Analysis
* **`etym-summarize [path] [--json] [-o <file>]`**
  Prints high-level dictionary statistics including Parts of Speech frequency, Language Origin distribution, and a Cross-Tabulation matrix of the top POS × Lang combinations.
* **`etym-affix [path] [--prefix|--suffix] [-n <len>] [-p <pos>] [-l <lang>]`**
  Performs a morphological frequency analysis to calculate the most common prefixes or suffixes across the dictionary, with optional filtering by Part of Speech or Language Origin.
* **`etym-select [pattern] [--starts|--ends|--exact] [--fold] [--length <n|n-m|n+>] [-d <path>] [--me|--inglisce] [--pos] [--bare|--count|--json]`**
  Selects entries by their **headwords only** — the `[ME]` line and the reformed line — and prints both sides of the reform for each. This is the narrow counterpart to `etym-find`: a search for `cion` there returns etymology forms, Middle English spellings and source URLs alongside the reformed forms you wanted, because it greps whole files.

  ```bash
  etym-select cion --inglisce          # reformed forms containing "cion"
  etym-select cion --inglisce --ends   # ...ending in it
  etym-select tion --me                # English headwords containing "tion"
  etym-select c̃ --inglisce             # every form carrying c-with-tilde
  etym-select ough --me --length 6     # two criteria at once
  etym-select --length 4-6             # length alone
  etym-select cion --inglisce --bare   # pipeable list of matches
  ```

  `--me` / `--inglisce` picks the side that is **searched, measured and sorted**; both columns print either way. At least one of a pattern or `--length` is required. The path is `-d/--dir` rather than a positional, unlike `etym-affix` and `etym-summarize`, because a pattern and a path are both arbitrary strings and `etym-select cion s` could not otherwise be told from a two-word query.

  **Checking a rule against itself.** The pairing of criteria is what makes this useful for auditing drift: 541 English headwords contain `tion` but only 438 reformed forms end in `cion`, so the difference is a list of words the rule has not reached — or has deliberately been spared.

  **Matching is literal, not regex**, for the reason `etym-find` uses `grep -F`: punctuation in a query can never become a pattern. ASCII case is folded, so the two entries beginning with Cyrillic `Ћ` are reachable by `Ћ` but not by a lowercase form of it.

  **Both query and form are canonically decomposed before comparison.** The dictionary writes the same letter two ways — `â` appears as U+00E2 six times and as `a`+U+0302 a thousand times — so without that step a search for `â` returns six hits of a thousand and reads as a wrong answer rather than an encoding mismatch. The table in `jq_defs` covers the base+mark combinations the orthography currently uses and must be extended alongside it.

  **By default the pattern then matches the form as written, marks included**, so `c̃` finds c-with-tilde rather than every c. The cost is that a query spanning a marked letter can miss: `ac` will not match `âc`, because a combining circumflex sits between the two letters. `--fold` strips marks from query and form alike, which makes `ac` match `âc` — and makes `c̃` match every c, so use it knowingly.

  **Length means letters, not bytes or codepoints.** `tône` is five codepoints and four letters; since roughly 40% of reformed forms are accented, a raw count would be wrong more often than right. Marks, hyphens and stray punctuation are stripped before counting and again for the sort key, so `âge` files at 3 and sorts at "age" rather than after z. Table padding uses display width, so accented rows line up.

  **Rows are deduplicated by headword pair.** The dictionary's ~8,800 stanzas are only ~7,800 distinct English–Inglisce pairs, because some 1,500 headwords carry more than one stanza — without dedupe `like` appears five times. Pass `--pos` for one row per stanza with its part of speech. Genuinely distinct reformed forms still get their own rows (`work → uirc` and `work → uirche` both appear).

  **Caveat inherited from the parser.** `resolve_me_word` keeps only the first comma- or space-delimited token of the `[ME]` line, so multi-word headwords collapse: ten entries match `New` as a prefix (`Noueórc`, `Nouhampsior`, `nouhampsioraït`), and `all` picks up `alraidy`, `altogaiþre`, `alþó`. The reformed side truncates the same way (`beehive → bí`, `toothbrush → touþ`). This is pre-existing behaviour rather than something the selector introduces, but a headword query is where it becomes visible — and worth fixing before anything writes to disk against a selection.

  Selection is the durable part of this function. Further criteria (POS, language origin) belong here as siblings to `--length`; anything that *acts* on a selection belongs downstream of the projection.

### Build Pipeline
* **`etym-build-dataset [output_file]`**
  Crawls the dictionary directory and writes the master dataset JSONL (default `toolkit/dist/master_dataset.jsonl`). This is the primary input source for Node.js build steps. Runs the parser as a single process over the whole tree.
* **`etym-flatten [path] [--jsonl|--csv] [-o <file>]`**
  A flexible flattening command that delegates to `etym-build-dataset` for JSONL, or compiles the dictionary into `dist/master_dataset.csv` for spreadsheet analysis. The CSV carries only `me_word`, `inglisce_word`, `pos` and flattened `conjugations` — etymology and sources are JSONL-only.

### File Management & Auditing
* **`etym-lint [path] [--strict]`**
  Scans the dictionary for formatting errors and returns exit code 1 if any `[FATAL]` or `[ERROR]` is found. Checks:
  * `[FATAL]` empty files
  * `[ERROR]` missing or malformed language tag `[]`, and a language tag sharing a line with a POS tag
  * `[ERROR]` a stanza whose conjugation line has no `(pos)` tag — silently dropped by `etym-parse`
  * `[ERROR]` a stanza with no reformed line and no etymology either — malformed rather than unfinished
  * `[ERROR]` a `(pos)` tag that is not at the end of its reformed line — `etym-parse` records an empty `pos`
  * `[ERROR]` source URLs separated from their stanza by a blank line — `etym-parse` reads paragraphs, so those sources are dropped
  * `[WARN]` trailing whitespace, stanzas with no resolvable language tag, and POS tags absent from `parts-of-speech.tsv` (these records are otherwise silently skipped by `buildBrain`)
  * `[WARN]` a stanza carrying etymology but no reformed line — a word not yet reformed. It warns rather than errors, because it is ordinary work in progress, but it warns at all because `etym-parse` drops the stanza and it reaches no dataset.

  Also generates a verb conjugation coverage report highlighting non-standard stanzas. **`--strict` is currently accepted but has no effect** — it is parsed into a variable the function never reads.

  **POS tag validation uses `etym-parse`'s own regexes**, so lint and parser cannot disagree about what a valid tag looks like. The check this replaced kept a second dialect of them — `\([a-z ]{1,5}(, [a-z ]{1,5})*\)` — which capped every tag at five characters and so rejected `(interj)`, `(suffix)`, `(prefix)` and `(intr v)`, all of which the parser accepts and all of which are registered. Being file-level rather than per-stanza, it also passed a file whenever any one stanza carried a valid tag, so it only ever surfaced on single-stanza files. Shape is settled by the parser's regex; membership is settled by `parts-of-speech.tsv`. Those are the only two authorities and neither restates the other — which is what keeps a bug like that from recurring.

* **`etym-trim [path]`**
  Strips trailing whitespace from all `.txt` files in a directory. Resolves all trailing whitespace lint warnings in one pass.
* **`etym-create-histories [-d] [-v] [--dirs <a,b,c>]`**
  Splits each multi-stanza `.txt` file into individual per-definition history files under `data-text/histories/`, named `<word>_<pos>.txt`. Non-alphanumeric characters in the POS tag become underscores, so `(adj, m n)` yields `..._adj__m_n.txt`. `-d` dry-runs without writing; `--dirs` limits the pass to named letter directories.

### Graphing & Visualization
* **`etym-graph [path] [-o <file>]`**
  Builds a `{nodes, edges}` JSON graph of all etymological relationships across the dictionary, default `etym_graph.json` in the working directory. Requires jq 1.6+ and checks the version explicitly before running.
* **`etym-visualize [graph_file]`**
  Converts a graph file (default `etym_graph.json`) into a Mermaid Markdown file, `etym_graph.md`, for visual preview in modern editors.

## 🧪 Testing

Two entry points, one source of truth:

```bash
npm test                        # full Vitest suite: bash + node + nlp projects
bash toolkit/tests/test-etym-parse.sh   # parser suite with ZERO npm dependencies (CI/quick shell loops)
```

* **Golden files** — every fixture in `tests/fixtures/parser/` (real dictionary entries covering all conjugation classes, hostile escaping cases, and multi-stanza files) is byte-compared against its frozen output in `tests/snapshots/parser/`. To refreeze after an intentional parser or fixture change:
  ```bash
  find tests/fixtures/parser -name '*.txt' | sort | while read f; do
    rel="${f#tests/fixtures/parser/}"
    awk -f etym-parse.awk "$f" > "tests/snapshots/parser/$(echo "${rel%.txt}" | tr '/' '_').jsonl"
  done
  ```
* **Schema contract** — `tests/node/brain-contract.assertions.mjs` pipes the frozen goldens through the real `buildBrain()` and asserts on the compiled brain, catching any drift between the awk parser and its Node consumers. It runs both under Vitest and standalone (`node tests/node/brain-contract.assertions.mjs`).
* **Property & fuzz** — `resolveForm`'s silent-ending rules are exercised across hundreds of seeded generated roots, and random hostile strings are round-tripped through the parser's JSON escaping. Seeds are fixed, so failures always reproduce.
* **Drop accounting** — the parser test asserts that *only* explicitly registered stanzas are ever skipped, so silent data loss in fixtures is impossible.
